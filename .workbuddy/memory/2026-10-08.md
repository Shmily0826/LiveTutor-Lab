### Decision

### Why not B (N.E.K.O as substrate)

- **Teaching layer 0%.** Not experimental, not abandoned — absent. Verified by
  reading grep matches, not counting them: 146 hits for `exercise` are the English
  verb; `quiz` appears only in prompt strings; `textbook` only in code comments.
  Only "tutorial" in the product is seven-day onboarding.
- **Desktop shell closed.** `N.E.K.O.-PC` → 404. Only distributable is a 213 MB
  NSIS installer; `/S` silent install → rc=1; documented channel is Steam. A
  Win32 control experiment proved the GUI subsystem works, so this is a
  *packaging* limit, not an environment limit.
- **Capture is renderer-bound.** `/api/capture/health` → 503 `no_renderer`. No
  headless operation, and capture cannot be tested without a GUI.
- **No AEC.** Echo handling is `difflib.SequenceMatcher` text similarity. Fine for
  a chat avatar, a correctness problem for a tutor that interrupts itself.

Adoption would not reduce teaching work — it would relocate it onto a substrate
that cannot be audited or fixed locally. The 30 % vs 55 % coverage framing is the
wrong comparison; both roads require writing the teaching layer.

### The one positive result worth keeping

**External Brain attachment works without forking — proven live.** A
`ThreadingHTTPServer` registered two custom tools via `POST /api/tools/register`
(per-tool flat schema: `name` + `callback_url`), they appeared in the agent role
(`affected_roles: ["YUI"]`, `source=livetutor_brain`, `is_remote=true`), callback
URLs are loopback-enforced (public host and 169.254.169.254 both rejected 422),
and unregister returns the tool list exactly to baseline.

But the extension point is **tools, not the brain**. N.E.K.O's agent loop is
in-process and owns the turn. Restoring Brain as the brain means replacing that
loop = a fork. The no-fork property holds only at the tool layer, which is not
where LiveTutor's value is.

## INCIDENT: killing N.E.K.O hides the user's mouse cursor — reproducible

**This will happen again.** Do not hard-kill N.E.K.O; quit it from the UI/tray.

### What happens

`src__system-cursor-visibility-service.js` (in the asar) builds a **32x32 fully
transparent cursor** (`CreateCursor`, AND mask all `0xFF`, XOR mask all `0x00`) and
`SetSystemCursor`'s it onto **18 cursor IDs**:

```
32512 32513 32514 32515 32516 32640 32641 32642 32643 32644
32645 32646 32648 32649 32650 32651 32671 32672
```

It then blocks on stdin waiting for the line `restore`; only then does it run
`SystemParametersInfo(SPI_SETCURSORS)` in a `finally` block.

**A `TerminateProcess` kill skips the `finally`.** Every one of those 18 cursors stays
transparent. Visible symptom: mouse cursor gone entirely (the cat-paw the user saw is the
same mechanism, with a real image instead of a blank one).

### The fix (scripted, verified)

`scripts/fix_cursor3.py` — reloads all 18 from `C:\Windows\Cursors\*` with
`SetSystemCursor`. Restores **17/18**.

Notes:
- `SPI_SETCURSORS` returns rc=0 / err=6 in this non-interactive session — ignore it,
  `SetSystemCursor` already applied live.
- **32640 (`IDC_SIZE`) cannot be set at all** (rc=0, err=0 for every file). It is an
  obsolete slot superseded by SIZENS/SIZEWE/NWSE/NESW/SIZEALL; leaving it transparent is
  harmless.
- The registry scheme (`HKCU\Control Panel\Cursors`) stays `Windows Default` throughout —
  checking it is a **red herring**. `SetSystemCursor` mutates live cursor objects, not the
  scheme. Don't waste time there.
- `GetCursorInfo` reports `CURSOR_SHOWING` the whole time — also a red herring. The cursor
  is "shown", it just has no pixels.

### Preconditions going forward

- Quit N.E.K.O from its UI, not by killing the process.
- If a kill is unavoidable, run `scripts/fix_cursor3.py` immediately after.
- Files used: `beam_m.cur` (IBEAM), `cross_m.cur` (CROSS), `aero_helpsel.cur` (HELP 32651),
  `aero_pin.cur` (32671), `aero_person.cur` (32672); the rest are the standard `aero_*`.

## Source-level root cause: cursor hiding is TUTORIAL-DRIVEN (found 2026-10-08, read-only)

Confirmed by reading `benchmarks/raw/asar-src/src__main.js` and
`benchmarks/raw/neko-app/resources/bin/static/tutorial/core/universal-manager.js`:

- `src__main.js:1343` creates `systemCursorVisibilityService`; every call site
  (`src__main.js:3850-3990`) is `activeTutorialSystemCursor*` / `clearTutorialSystemCursor(...)`
  / `replaceTutorialSystemCursorLifecycle()`. **The system cursor is only hidden while the
  tutorial is running.** The "cat paw" is N.E.K.O's own drawn cursor during tutorial takeover.
- Tutorial completion persists in localStorage: `universal-manager.js:4074`
  `localStorage.setItem(getTutorialStorageKeyForPage(page), 'true')`, read back by
  `hasSeenTutorial()` at line 4275. Home page instead uses the seven-day state, persisted
  server-side at `/api/seven-day-tutorial/state` (`tutorial/core/seven-day-state.js:15`).
- **The destroy path returns BEFORE the persist.** `universal-manager.js:4060-4068`: if
  `endMeta.reason === 'destroy'` it returns early. So a hard kill during the tutorial records
  NO completion. Next launch replays the tutorial, re-arms cursor hiding, and killing it again
  transparentizes the 18 cursor slots all over again. This is the exact loop the user feared.
- Skip DOES persist: the localStorage write at 4074 precedes the `reason === 'skip'` branch at
  4077. Skip controls: `#neko-tutorial-skip-btn`, `[data-yui-skip-control]`,
  `[data-yui-emergency-exit]` (`tutorial/core/skip-controller.js:8`,
  `app/app-interpage/guide-message-relay.js:470`, `tutorial/yui-guide/overlay.js:1362`).

## Round 7 (22:50-23:05): Stage 2 diagnosis — `capture_busy` root-caused, narrowed to ONE leaked global

Reproduced deterministically, then isolated the fault. No source touched, no restart performed yet.

**Reproduction (the cleanest possible form).** The Study plugin calls the interactive screenshot
API over loopback via `httpx` with NO `Origin`/`Referer` header. `screenshot.py:313-314`
explicitly documents that pure server-side loopback calls may SKIP CSRF exactly for
curl/local scripts. So a curl with no Origin is a faithful stand-in for the plugin. Result:

```
no Origin  -> 409 {"success":false,"error":"capture_busy"}    <- plugin's exact path
with Origin -> 403 csrf_validation_failed                      <- a separate, correct guard
```
The earlier confusion ("CSRF blocks everything") was wrong: CSRF is not on the plugin's path at
all. **`capture_busy` is genuine, not a header problem.**

**Fault isolation — the neighbour channels are healthy.** With the same no-Origin invocation:
- `GET  /api/capture/health`                      -> `{"success":true,"available":true}`
- `POST /api/capture/screenshot` (target_id+pid+title) -> **HTTP 200, 364 KB PNG (1666x1080)**,
  decoded and saved as `evidence/stage2-bridge-window.png` — it visibly shows the character panel.
So the renderer is registered and the capture bridge works. This rules out "no renderer",
"bridge dead", "renderer wedged" and leaves the interactive path specifically broken.

**Root cause.** `utils/capture_bridge.py:93` holds a module-global pair
`_interactive_capture_active` / `_interactive_capture_token`. `request_capture_region` (line 416)
sets `active=True` under `_interactive_state_lock` and raises `capture_busy` at line 417-418
whenever it is already True. It is cleared ONLY by `_release_interactive_capture` (line 512),
which is called from the `finally` at line 483 — *unless* `retain_busy_until_renderer_stops()`
already ran (line 441-453), which flips `release_on_return=False` and defers release to a
background task that waits for the renderer future, capped at `session_timeout_ms`. The backend
process (pid 3812) has been up ~132 min and `capture_busy` never once cleared in that lifetime;
the Main log contains no region-session start/timeout/done line at all. So the flag was latched
True by an earlier session and its release path never completed.

**Two candidate leak mechanisms (not yet discriminated; both fit the evidence):**
1. The renderer never answered (overlay closed by app teardown / focus change) so the
   background `wait_for_renderer` task is still parked on a future nobody resolves. Note the
   adjacent Plugin_error.log shows `StudyEventBus._consume_queue()` repeatedly dying with
   `<Queue ...> is bound to a different event loop` and `ConnectionResetError 10054` — this
   process clearly loses renderer connections, which is exactly how the future would be orphaned.
2. The overlay is genuinely still up on a desktop/monitor state the current session cannot see,
   so no release was ever supposed to happen.
Discriminating them needs a backend restart (mechanism 1 disappears on restart; mechanism 2
survives only if re-triggered) — see the restart plan.

**Design defect worth recording, independent of the leak.** `entry_ocr_entries.py:79-110`:
`capture_mode="interactive"` only falls back to fullscreen for the whitelist
`{no_renderer, main_server_unavailable, interactive_unavailable}`. `capture_busy` is NOT in it,
so at line 104-109 the whole OCR entry returns `Err` and the user gets an opaque failure —
there is no recovery path for a stuck lock short of restarting the backend. That is the part
of this gap that is a product bug rather than an environment state.

**Restart plan (owner-checked, reversible).** pid 3812 is proven owner of 48911 by
`netstat -ano`. Restart = stop 3812 only, relaunch via the lab launch script, then re-run
