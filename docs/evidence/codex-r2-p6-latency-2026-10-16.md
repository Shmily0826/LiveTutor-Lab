# P6：工具结果大小与首个 provider 音频包

原真人日志的约9秒仍属于“工具结果提交/所有权启动→首个provider音频包”区间，不能进一步分成provider计算、网络或接收等待；没有足够证据认定本地arbiter排了9秒。原场没有记录完整序列化结果体大小，不能用SQLite教师回复长度冒充它。

本轮只读比对现有真实Native场的wire function_call_output字节数与同输入轮下一首包。原始表：raw/evidence/codex-r2-p6-latency.json；共13个输出，其中1个561-byte的范围拒绝单独排除教学质量比较。

12个成功教学输出体范围1967–2566 bytes；区间2.395–6.539s，中位数2.870s。较小输出也会更慢，当前观察不支持“结果体越大就导致那9秒”的结论；这些是不同场的观察，不是A/B或因果证据。

旧relay正文209 bytes，P3为完整逐句复述改为161 bytes；这是语义修复，没有进行延迟A/B，也不声称缩短48 bytes带来了性能提升。现有结果体约2KB，未发现明显的结果体膨胀或有价值的可删内容，因此没有为P6新增4场压缩实验，也没有采用性能专用的payload变更。

结论：**只读诊断完成，延迟根因仍未确定**。9秒与目前固定WAV场不是同一上下文，不能据较短数字称真人延迟已修复，更不能归咎provider。未触碰宿主/arbiter/打断/传输。本项新增外呼0，可听性与真人均未验证。
