# 首声延迟归因（离线汇总，2026-10-23）

> 只用已存盘的真实计时（10-15 的 M2/M5 场、10-16 的 R5 场）与源码阅读。
> **没有新 Native 场、没有外呼、没开麦、没发声。** 账本仍 1825（停线 1861）。
> 所有"可省多少"都是**基于已测分段的估算**，不是实测；任何改动都要 A/B 才算数。

## 一、结论先行

1. **现状不是"7–11 秒随机"，最快路径已经压到 7.81 s**（fresh-2，10-15），10-16 的固定 WAV 场复现 7.4–7.8 s。
2. 14.69 s 那个数字属于 **M1 之前**（run 70），工具内部还没做指纹跳过、路由还没与源码读取并发。
3. 剩下的 7.8 s 里，**四个串行段各占一份**：识别 ≈1.3 s、触发 ≈0.5 s、工具 ≈3.3 s、音频首包 ≈2.7 s。
4. **用户感知的痛点是"这 7.8 秒里完全无声"**，不是 7.8 这个数字本身。m2 报告原话："工具约 10 秒期间没有任何反馈"。
5. 真人场约 9 s 与固定 WAV 的 7.8 s 之间那 1–2 s，**没有分段数据**，属于观测缺口（见第四节）。

## 三、还能砍什么（按风险从低到高）

### A. 路由与讲解合并成一次调用 —— payload 层，风险低

现在是**两次串行 LLM**：先问"该读哪些文件"（1.98 s），再问"讲这个文件"（0.79 s）。
当用户已经明确指定文件或上下文里只有一段源码时，路由这次调用是**可以省的**。
m2 报告已经证明路由与源码读取能并发（路由只额外等 0–12 ms），说明这条链本来就可压缩。

- 估算收益：**1.0–1.8 s**
- 代价：路由准确率可能下降（选错文件）。必须有离线评测集（已有 13 题评测集）兜底
- 是否动宿主：**否**，只改 payload
- 判据建议：13 题评测集上文件选中率不降，首包中位数至少 −1.0 s

### B. 等待期给一句**语音**，而不是一行文字 —— 风险中

现在工具开始 1.5 s 后会弹文字"正在查看源码……"（`neko_study_wait_notice_patch.py`，已被 Native 证据确认在转写后约 2 s 出现）。
但那是**屏幕上的一行字**，用户戴耳机时根本不会看。

- 估算收益：**感知延迟从 7.8 s 降到约 1.5–2 s**（不减少真实延迟，只消除沉默）
- 代价：可能和正式回答抢话；需要一条"播完就停"的短音频路径
- 是否动宿主：**是**（语音传输层）。按项目规矩必须先商量，不能自己动
- m2 试过让**模型**先说一句再调工具 → provider 空回合（m2-1），已撤回。那次失败的是"经过模型"，不是"插一句固定语音"

### C. 音频首包 2.7–3.0 s —— 风险高，先别碰

这段是 TTS/实时音频链路的固有延迟。10-16 已经因为碰传输层出过事故（`audio_frame_blocked` 静默丢帧）。
除非 A、B 都做完还不够，否则不动。

## 四、观测缺口（这才是复测时最该补的）

- **真人场没有分段数据。** 所有分段来自固定 WAV 场。真人场"约 9 s"只是一个总数，
  不知道多出来的是 ASR（口音/停顿）、工具（不同 store 首次同步），还是音频首包。
- 下次真人复测时，如果能让宿主日志记下四个时间点（ASR final / tool start / tool return / first audio.delta），
  这个缺口就永久关闭。**这比再跑几场问答有价值。**

## 五、建议顺序

1. **复测时顺手采分段数据**（改日志不发声、不花额度），先把真人场那 1–2 s 变成可归因的数字
2. 然后做 **A**（payload，低风险，收益 1–1.8 s）
3. 再看要不要商量 **B**（感知层，收益最大但动宿主）
4. **C 不做**

本报告没有验证任何一项改动，也没有跑新场。第 2、3 步都是估算，依据是上表的实测分段。
把"估算"当"结论"用，是 10-16 那三轮反复自我更正过的同一个坑，这里不重犯。
