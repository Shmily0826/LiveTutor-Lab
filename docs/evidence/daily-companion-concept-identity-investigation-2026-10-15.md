# Course concept identity — readonly investigation

Status: confirmed SOURCE cause with a small OFFLINE method fixture; **no fix implemented**. No learner database, provider, host, audio/device, manifest, budget or shared state was modified. This investigation did not query the actual C41 DB. Only the relevant task-owned41/42 request/result fields, the three requested source files and existing topic tests were read.

## Confirmed split and scope

Original41's adjacent/reversed/correct calls and42's correct-equivalent call all supply only `question`, `expected_answer`, `answer`, with no qid, aid or selected_topic_id. Their question SHA is identical (`0eac34584c4c37b892182d61253fc8ebb53766bbdbcd1619532c69b9d94948dc`). The41 results return course-scoped `有向关系`, taken from the model's first related topic;42 returns course-scoped `directed relations`. This independently corroborates Main's reported QA topic split without reading or rewriting those rows. Preserving old QA hashes does not preserve the concept identity used for new mastery/FSRS updates.

The mechanism is **not exclusive to SDK transport**. The observed41/42 scene is an anonymous supplied-question entry case, but any held question with qid/aid and no stable topic can reach the same fallback. A held question that already carries a nonempty selected_topic_id / topic_id / topic has stronger protection: current-question grading copies and prioritizes it, rejects a conflicting supplied selected topic, and retry copies the held question while changing only its attempt/retirement state. That protects this same held question across a reply-language change, not every independently generated question about the same concept.

## Exact selection / write chain

1. `entry_tutor_answer_entries.py:184–293`: determines current versus supplied question, validates held qid/aid, copies current payload only for held-question use, then chooses held selected_topic_id / topic_id / topic. Supplied questions without an explicit selected topic begin with no topic identity. The selected value is attached to question_payload and context before the model. Later grading sets public topic to this selected identity for a held question; it does not derive a stable concept merely from qid/aid.
2. `entry_tutor_context_support.py:1023`: `_track_learning` prefers context.selected_topic_id, question_payload.selected_topic_id / topic_id / topic, then model eval.topic, first model related_topics, question text, general. With no authoritative topic, the model's learner-facing language controls the fallback label.
3. The same file at1094 uses that track topic before eval.topic, writes it into a copy of the question payload, and prefixes `course_id + '::'` before `KnowledgeTracker.on_answer`. This prevents two courses sharing a topic key, but not one course receiving multiple translated keys. It does not backfill a formerly empty live held-question topic: `_record_tutor_result` stores last evaluation, while tracking uses a copied question payload. A later retry can still lack an authoritative topic.
4. `knowledge_tracker.py:1372–1401`: `_resolve_and_identify_topic` selects the given topic, then `_resolve_topic_id` returns any already course-scoped `::` value verbatim. Such labels bypass graph/name spelling canonicalization. The graph's existing name canonicalization at324 and `_canonical_topic_name` at68 handles only case/space/punctuation, intentionally not translations.
5. `KnowledgeTracker.on_answer` / `_on_answer_batch` / `_prepare_answer_topic_data` uses this selected key for recent evidence, mastery, QA, wrong-question and FSRS/review writes. Distinct scoped labels consequently can create distinct runtime topics and progress histories; this is not merely a display-name discrepancy.

## Minimum evidence-based next step

Reuse existing selected topic / question payload / course-scoped SQLite records, with identity chosen **before** any model await:

- Prefer an explicit validated current-course selected_topic_id or an already pinned held-question topic. Preserve it through grading, retry, restart and display-language changes; model `related_topics` remains descriptive text and cannot replace that identity. A generated question should carry the selected existing concept ID from its source rather than only a localized topic label. For topic-less held questions, establish and persist a stable topic binding once under the existing exact qid/aid/course/session/material guards before evaluation; do not pretend an old owner or arbitrary new course still matches after an await.
- For an anonymous supplied question, the immediate supported caller interface already accepts selected_topic_id: repeated evaluation can reuse an explicitly chosen existing course topic. Do not present a model-invented translated label as that explicit authority. Enforce course/provenance consistency rather than nesting another course prefix or silently reading a new course.
- If automatic same-question reuse is needed, use a bounded readonly lookup of existing QA question JSON / course / original question / expected answer and applicable material provenance, and reuse a topic **only if one unambiguous identity is evidenced**. Do not use one arbitrary/latest result or merely matching answer text. The41/42 store already has multiple identities for that same question; that conflict requires an explicit binding decision for future records, not silent selection of one as if no ambiguity existed.
- With no evidence of an existing concept, a deterministic original-question/provenance identity can be a safe **same-question-only fallback**, stored in the existing question/topic mechanism. It must be named/documented as provisional question identity, not a multilingual concept equivalence. Changing question, expected answer or material scope must not automatically reuse it. Cross-question concept reuse should use an actual known topic/explicit learner selection; no translation service or global bilingual word list is warranted.

Do not update, merge, delete or relabel old QA, old grades, mastery or review rows just to make the next test look unified. A future read/display association of explicitly proven equivalence must retain original provenance; it is a separate audited change, not this minimum fix. No global Chinese/English label guessing or new memory store is proposed.

Before a real follow-up, a temporary SQLite actual-entry test should grade the same held question in two output languages and retry with a new attempt: same topic / one mastery+FSRS identity, distinct preserved QA/attempts, expected prior rows unchanged. Also cover no-topic held input, anonymous supplied input, ambiguous historical topics, two different concepts in one course, same question text with changed reference/material, course switch/restart and failures at the existing short commit guards. These tests are proposed, not executed here. The next change should report same-question continuity separately from cross-question concept identity.
